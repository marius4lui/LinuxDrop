# LinuxDrop visual review — 2026-10-06

Read-only review of the existing PNG captures in `docs/acceptance/ui` and current GTK/Shell source. No live desktop input, browser, new demo, or rendering was performed. Source was changing concurrently; the items below describe the inspected implementation and should be reconciled with the desktop owner's subsequent edits.

The native preferences rows, restrained card borders, light/dark backgrounds, and explicit primary/secondary confirmation actions form a good base. Preserve these. Avoid filling the Transfers page's unused space with decorative content.

## Prioritized changes

1. **P1 — Make recipients visible in a small Send window.** `app/linuxdrop/src/ui.rs::build`, send `body`/`drop`; `resources/style.css` `.drop-zone`, `.drop-icon`. In `send-dark-en-480x600.png`, the large idle drop illustration and stacked introduction occupy essentially the entire scrolling viewport; Nearby is absent. Current source retains 30px drop padding, four stacked children, 20px body gaps, and 24px top margin. Make the idle drop a compact horizontal icon/text/action arrangement, approximately 100–120px high; use 12px body gaps and 16px top padding, and collapse redundant introductory copy at compact heights. **Accept:** at 480×600, EN and DE, both themes, initial viewport shows the file action, Nearby heading, and first recipient or useful empty-state text above the send footer. At 420×480 all actions remain reachable without horizontal clipping.

2. **P1 — Bound selected-file presentation before Nearby.** `ui.rs::render_files`, `file_box` appended before peer list. The current unbounded loop makes every chosen file push recipients farther away; new per-file size/error subtitles increase this effect. Show a compact count/size summary and at most two rows, with an explicit expandable file list; bring invalid selections into view when needed. **Accept:** 1, 10, and 100 selected files do not cause the collapsed draft preview to grow indefinitely; recipients remain visible/reachable and all filenames, removal actions, and validation errors remain accessible through expansion. This is source evidence; the existing two-file capture predates the added metadata rows.

3. **P1 — Give German bubble actions enough width.** `extensions/gnome-shell/extension.js::_renderBody/_button`; `.linuxdrop-notch-actions` and `.linuxdrop-notch-action`. Current verification uses three same-row buttons inside a 350px bubble, including the translation “Codes stimmen überein”; terminal states can also contain three buttons. This cannot be treated like the short two-button English idle capture. Put the primary verification action on its own full-width row, with Decline/Details below; arrange three terminal actions as two rows. Use compact previous/next icon buttons plus a central count for multi-transfer navigation instead of two long translated labels. **Accept:** DE/EN verification, terminal success/error, and multi-transfer states fit the 350px bubble at normal and increased text size; every label is complete and focus outlines remain inside the surface. This is a current-source layout risk, not a rendered verification failure.

4. **P2 — Keep wide-window navigation and footer aligned with content.** `ui.rs::page/build`: content uses `adw::Clamp(maximum_size=760, tightening_threshold=560)`, but `send_bar` is appended outside that clamp, and bottom navigation is always revealed. Wrap the send footer in the same width-constraining composition and synchronize its outer edges with the body. At approximately 760px and above, use a wide-policy native `adw::ViewSwitcher` in the header and hide `ViewSwitcherBar`; retain the bottom switcher and window title below that threshold. **Accept:** at 800, 1000, and 1400px widths the action panel does not stretch across empty side margins, one navigation control is visible, and Send/Transfers/Hardware/Settings remain balanced. The 800px Hardware capture verifies the current bottom-only navigation; wider Send geometry is source-derived.

5. **P2 — Separate actionable transfer state from protocol metadata.** `ui.rs::render_transfers`; `.protocol-badge`, `.compact-note`, `.empty-text`. Incoming/completed captures show the critical state combined with the protocol in an 11px, 0.66-opacity line; empty-device guidance and send instructions are similarly subdued in light mode. Keep protocol metadata secondary, but render “Wants to share with you”, verification, failure, and completion in a distinct normal-opacity 13px label, using a symbolic state icon where useful. Use at least 0.75 foreground opacity for essential secondary instructions, then measure rendered contrast rather than relying on opacity alone. **Accept:** state can be identified without reading tiny metadata; essential normal-sized text meets 4.5:1 against its actual light/dark background. Disabled controls keep native disabled styling. No numeric contrast measurement was performed in this pass.

6. **P2 — Constrain arbitrary transfer text inside the bubble.** `extension.js::textLabel/_renderBody`. Current helper enables wrapping and disables ellipsization, but does not specify word/character wrapping or a line budget; peer names, single filenames, and backend error strings feed it directly. Use `Pango.WrapMode.WORD_CHAR` for explanatory/error text, cap the collapsed description to a small readable number of lines with a Details action, and use middle ellipsis plus an accessible complete label for long filenames. **Accept:** an 80-character unbroken filename and long German peer name/error cannot widen the bubble or push actions off the visible monitor. Existing `panel-open.png` has a truncated idle sentence, but the wrapping helper has since changed, so that image alone does not prove current clipping.

## Capture age and already addressed issues

- Older 18:35–18:47 captures show a permanently visible narrow capsule with truncated title; the 19:07 `panel-open.png`/`panel-closed.png` and current `visible: false` plus `_expanded` gating represent the newer panel-first design. Do not reintroduce the capsule.
- The old Hardware capture contains a raw multiline BlueZ D-Bus error. Current `render_hardware` already replaces this common case with a short human-readable summary and moves technical detail to a tooltip.
- Incoming/completed captures contain English state text inside the German UI. Current `render_transfers` calls `tr(status)` and formats German byte progress; translations and new renders must decide remaining status, not the old image alone.
- Existing Settings captures show native, readable grouped rows, but precede current category controls and the full settings inventory. No current rendered claim is made for those additions.
- For known-device management, preserve a clean Send surface: one “Manage devices” action by Nearby opens native grouped device rows; place per-device favorite/rename/block actions in one overflow menu rather than exposing multiple controls on every peer card.

Desktop implementation owner and root were notified of the highest-priority findings. Final rendered acceptance should be targeted at the layouts above and must not disturb the user's active demo.
